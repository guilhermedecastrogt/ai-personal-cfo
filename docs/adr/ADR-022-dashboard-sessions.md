# ADR-022: The dashboard signs in with member access codes and server-side sessions behind the web server

- Status: Accepted
- Date: 2026-10-05

## Context

Until now the only way into the system was WhatsApp, where the sender's number identifies the member. A browser has no such identity, and the dashboard shows a household's complete finances.

The project has deliberately avoided building account management: no email addresses, no passwords, no sign-up. The dashboard still needs a real authentication boundary, and it has to produce the same thing identity resolution produces for WhatsApp: a household and a member that the rest of the application can trust.

## Decision

**Access codes.** A member is given a long random access code, generated by the system. Only its SHA-256 hash is stored. Issuing a new code replaces the old one. Codes are issued by an operator through a script.

**Sessions.** Signing in with a valid code creates a session: a random token, stored as a hash with an expiry, tied to the member and household. The session guard resolves a bearer token to the request context used everywhere else.

**The web server sits in front.** The browser talks only to the Next.js server. That server keeps the token in an http-only, same-site cookie and attaches it to its own requests to the API. The API is never called from browser code.

**No identity in requests.** No dashboard route accepts a household or member. The household is whatever the session says.

## Alternatives considered

**Passwords chosen by members** need reset flows, strength rules and slow hashing. A generated 256-bit secret needs none of them and cannot be guessed, which is also why a fast hash is sufficient.

**A sign-in link sent over WhatsApp** would reuse the identity that already exists and is the natural next step. It depends on outbound messaging outside a conversation, which the WhatsApp integration does not do yet.

**Stateless signed tokens** avoid a sessions table. They cannot be revoked on sign-out without one, and revocation matters for financial data.

**Calling the API from the browser** would need the token in script-readable storage or cross-site cookie handling with its own protections. Keeping it on the server removes that surface.

**A third-party identity provider** is more than a household tool needs and would add a dependency to running it at all.

## Consequences

- The dashboard has the same authorization boundary as WhatsApp: a resolved household, taken from nothing the client controls.
- A session can be ended immediately, by sign-out or by deleting its row.
- An access code is a bearer secret. Anyone holding it can sign in as that member until it is reissued.
- There is no sign-in rate limiting yet. The size of the code makes guessing impractical, and limiting belongs with the general hardening of the HTTP surface.
- Members cannot obtain or replace a code themselves.
- The web server must be able to reach the API, and browser requests always pass through it.
